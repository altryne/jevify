# Field notes from agent sessions

Use these examples when a similar failure appears in your workflow. They are historical session observations without bundled run records, not reproduced benchmarks or universal rules. The current execution guidance is in [running-jev.md](running-jev.md).


Observed in real sessions. Each note is a misunderstanding the skill now tries to prevent.

- **Building first, discovering the missing key last.** Check the key at the start and ask once.
- **Hunting for credentials.** Environment and project env files only; then ask the user.
- **A serial request loop.** Correct batching inside each request, then one request at a time. Use `ask_many` or the async client.
- **One Choice for properties that can co-occur.** A sentence-role Choice offered "on topic", "abandoned restart" and "stage mechanics" as rivals, but a sentence can be on topic and contain a restart. It was rebuilt as one Noul per property plus a Score for how much the sentence is needed, composed in code. Split properties when their answers are independently needed. A Choice remains appropriate when the application needs one primary handler or best action, even if several alternatives could be suitable; define the selection rule.
- **A Noul framed as a counterfactual negative.** "If the bracketed words are deleted, does the meaning change?" returned middling probabilities on obvious cases. Rewritten so that yes is the plain, positive observation ("does the sentence still state the same facts without them?"), with `what` and `examples` on both `true` and `false`, it separated the cases. Make yes the direct thing you are looking for, and avoid stacking a hypothetical on a negation.
- **Criteria that only describe the interesting classes.** A relevance rubric written around digressions and logistics filed greetings, thank-yous and one-word fragments as low-value "off topic", because nothing in the criteria covered ordinary conversational glue. Describe the boring majority class too, or use a domain-specific exact filter when those items are outside the task. Length alone is not a safe filter for requests or feedback. The agent ended up rejecting about half of the flagged candidates by hand, which is the cost of skipping this.
- **One Choice over look-alike candidates.** Code generated dozens of candidate edits to a sentence, many nearly identical, and one Choice was asked to pick the right one. The probability split across the look-alikes, no option cleared the threshold, and 0 of 6 labeled cases were found. Choice options must be genuinely different outcomes. For near-duplicates, ask a Noul per candidate, let code pick the best, and merge candidates that produce the same result.
- **A small target judged inside a long text.** "Does this sentence contain a self-correction?" over a long sentence missed slips of two or three words, because everything else in the sentence diluted them. Show a short window around each candidate instead, and have code strip unrelated noise from that window so the question turns on one thing only.
- **Thresholding a question that does not separate.** One wording scored real positives 0.58–0.65 and clear negatives up to 0.56; a second scored 0.42 against 0.43. No threshold rescues that. Before choosing a threshold, look at the gap between labeled positives and negatives. If there is none, the question is the wrong shape: make it more literal, split it, or change what is shown. Revert a rewording that does worse, record that it failed, and when the gap stays small hand the user a ranked list of probabilities rather than a yes/no.
- **Leaving the unit of work unstated.** The user had to ask "how did you send this to Jev: per sentence, per paragraph?" Say in the deliverable what one request holds: how many items, how much surrounding context, how many questions per item.
- **Questions sent cold, with no domain context.** The user had to point out that Jev was never told what the material was or what the decision was for. See "Tell Jev what it is looking at" in [question-design.md](question-design.md); context helped some questions and hurt one, so test it per question.
- **A question that answers itself.** Criteria that named the target tokens produced the same answer for 99% of items. See "Check that the question is doing work" in [question-design.md](question-design.md).
- **Self-made labels reported as measurement.** "Measured: helps" rested on ten examples the agent chose and labeled itself, and the user called it out. See "Say who made the labels" in [evaluation.md](evaluation.md).
- **Judging the original after the user has changed it.** An interactive helper cached judgments by item number. After the user applied an edit, the remaining suggestions were still opinions about text that no longer existed, and nothing had judged the new join. Send Jev the current state (the text as edited), key the cache on a hash of what was actually sent rather than on an ID, and re-run when the state changes. At these latencies and prices, re-judging on every change is affordable.
- **Judging one unit and displaying another.** The server split the transcript into paragraphs by its own rule and the UI split it by a different rule for display. Suggestions then referred to text above and below what the user was reading, and swapped mid-play as the server's paragraph boundary passed. The user's expectation was the right spec: results for a unit are deterministic and stay put until something changes. Define the unit once, with one piece of code or by having the UI send the exact item range it shows, and use that same unit for state, cache key and display.
- **A semantic yes treated as safe to apply.** Every pack judged whether words should go; none judged whether the resulting splice would sound clean, and bulk-apply ignored the one audio warning that existed. Jev answers the question about the content; the quality of the action's result (an audio join, a code change that still compiles, a layout after removal) is a separate property that code measures from the medium itself. Compute that safety score per item, combine it with the Jev strength in the same ranking so unsafe items sink, and gate any bulk action on both. Build the safety measure before offering bulk apply, not after the user asks why the results are rough. Then calibrate it before it becomes a verdict: a first-draft "clean / rough" gate built from guessed thresholds was removed the same night because cuts it called clean were not, and a wrong verdict is worse than none. Until the user's accepts and rejects have set the thresholds, show the measurement as a fact on the item ("no quiet point at the start") and let the person decide.
- **Losing to the manual baseline on the user's clock.** After an evening of iteration the user said they would have finished by hand long ago and left for their usual tool. The packs were cheap and fast; the workflow around them was not: hundreds of proposals to review, rough results that needed checking by ear, and the user's time spent steering the build. Measure the whole loop (proposals produced, proportion accepted, review minutes per accepted change) against doing the task by hand, early and with the user, and stop or narrow scope when the loop is losing. Start with the smallest high-precision slice the user can act on in minutes, and grow from acceptance data rather than from what Jev can judge.
- **Only finding what the unit size allows.** Per-sentence and per-word packs surfaced hundreds of tiny cuts, and the user's reply was that none of them were the cuts that mattered. The changes with the most value (a minute of setup, a demo that never worked, a dropped guest) span many sentences and need the whole piece read against what has already been changed. Judgments at one granularity find issues at that granularity. Decide early which unit each kind of decision needs, give the large ones to Jev over wider bounded units with a source-linked overview, then retrieve the evidence needed for reasoning, and rank the deliverable by the value of each change rather than by count.
- **One threshold for everyone.** The user set the bar per slice: 0.9 for most speakers, then 0.78 and no join gate for one speaker whose speech was unfollowable without heavy cutting, accepting rough results there because understandable beat fluent. The right threshold depends on the cost of an error in that slice, and only the user knows it. Expose thresholds per slice (speaker, section, category) rather than one global number, and record which setting produced each accepted change.
- **Duplicates from near-identical spans.** A second pass posted a suggestion on a word that already had an accepted cut with slightly different edges, because dedupe only skipped candidates an existing action fully covered. When proposals are spans, treat any overlap with an existing action of the same kind as a duplicate, or merge the edges, before posting.
- **Tuning on the smoke set.** After a boundary run showed misses, the thresholds and code rules were adjusted and the same cases rerun. That is a fine way to fix a design, and the rerun is not evidence of accuracy. Say so, and hold out cases the design has never seen.

A later archive review exposed two separate losses. Whole-exchange importance scores undervalued short user goals and recurring friction. An authority Choice even labeled an explicit user question as assistant-only. Several high-scoring signals were then lost in the agent's synthesis. Preserve recorded roles in code, judge each user signal separately, aggregate recurrence across chunks, and check the draft against the evidence ledger. See [corpus-review.md](corpus-review.md). This diagnosis does not establish the accuracy of a replacement workflow.

Patterns from those sessions worth copying:

- **Mark the target inside the text** when judging one token or span in a sentence, for example `[[like]]`, and name the field for what it holds (`sentence_with_target_in_double_brackets`). A state path alone cannot point at the third word of a string.
- **Sum the Choice probabilities of the labels that lead to the same action** (`P(hesitation) + P(discourse_filler)`), and threshold the sum. The options compete, so the sum is a valid probability of "any cut label".
- **Check both the content judgment and the result of an edit.** A Choice for what a word is doing and a separate Noul for whether the sentence survives without it; code acts only when both agree, and abstains otherwise. One session reported no false cuts on its small labeled set, with some missed cuts. These judgments are not statistically independent and do not establish safety on other inputs.
- **Invent the examples in criteria.** Examples copied from the cases you will test on leak the answers and inflate the result.
- **Judge everything, act on a slice.** Save every judgment with its request hash, then let code post or apply results by window or by threshold without new calls. A reviewer gets 45 proposals to check rather than 1,200.
- **To find a span, judge edits.** Jev cannot return a span or rewrite text. Code proposes candidate edits (deletions around a repeated word, around a marker such as "sorry"), each shown as a short before and after pair, and Nouls ask whether the edit removed only the mistake and whether the result is what was meant. Code maps the winner back to exact positions.
- **Give the person a question lab when they want to iterate themselves.** Once the packs worked, the user wanted to write and try questions directly, and said hand-writing the JSON was hard. What helped: a small local page that lists the questions already in use, lets them write one question as a template (a placeholder such as `{unit}` that code renders into the backticked state path for each item), choose the unit (sentence, paragraph, segment), run it on real data, click results to label them, and save the keepers. Use form fields rather than a raw JSON box: a type switch labeled "Yes / No", "Pick one" and "Scale", plain inputs for what yes and no mean, rows for examples, options and levels. For labeling, offer a blind mode (answers hidden, random order), a sort by least certain, and a per-question setting for what a yes means (cut, keep, or information only) so opposite questions are not read the same way. Keep the API key on the server side of that page and bind it to localhost.
- **Show probabilities as plain-language evidence and as a slider.** Each suggestion carried one sentence built from the answers ("host operating the show 95%, about this segment's topic 8%, listener need 0.2 of 4") so the reviewer could see why without a generated rationale. Borderline items were not hidden by a hard threshold: everything was offered with its probability as a strength, and a slider in the UI set the bar, so a natural pause sank below the slider instead of vanishing.
- **State measurements in words.** Code measured the silence around each candidate from the audio and passed it to Jev as a description ("a long pause before, none after") rather than milliseconds, since Jev is weak with raw numbers and cannot hear.
- **Deadlines on the interactive path.** A user-facing helper put a 12 s abort on each Jev request and a 20 s abort on the page's own call, treated a timeout as "not judged", showed the error in the panel and offered a Re-run button, so a slow call could never leave the UI stuck on a loading state. Normal answers arrive in well under a second, so a short deadline costs nothing.
- **Decide in code what code can see.** "you know what…" has an object and is not a filler; a rule removes it from the candidates before Jev is asked.
- **Let the reasoning model do the one-off interpretation** (a topic map of the episode) and give Jev the repeated judgment inside it (the role of each sentence in its segment).
