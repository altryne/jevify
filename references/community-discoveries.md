# Community discoveries

Dated snapshots of first-hand community experiments, newest first. Every number below is reported by its author and was not reproduced for this skill. Treat a snapshot as examples of how evidence changes a design, and run fresh research for new discovery work.

## Snapshot: September 14–17, 2026

Method: last30days 3.18.4 with `--days=3 --as-of=2026-09-17`, then primary-source verification and web supplements. The engine returned 80 candidate items across eight sources, of which findings 1–7 below survived as first-hand and relevant. Reddit coverage was partial due to HTTP 429. Findings 8 and 9 were added the same day from posts the maintainer supplied.

**1. Parallel writing checks, not a single expensive overall critique.** Mike Taylor's September 15 report (updated September 17) describes 777 judgments across 37 documents in under 0.7 s for an estimated $0.0025. A separate 12-passage comparison reported 0.35 s median for Jev versus 8.83 s for Fable 5.1 at high effort, about 580× lower estimated cost, but Jev detected six of seven planted defects versus seven for Fable. Adaptation: turn a style/quality rubric into independent defect Nouls and let a generator repair flagged passages. Preserve a stronger review for misses. [First-hand Every report](https://every.to/also-true-for-humans/mini-vibe-check-typesafe-s-jev-judged-everything-i-ve-written-in-0-7-seconds).

**2. Memory selection needs “which ones,” not “which one.”** Aera's September 17 offline study reports 400 cases from one profile. For 276 unattended runs, the same-pool Jev selector matched 46% coverage, with 85% precision versus 79%, 147 ms versus 463 ms median, and estimated $0.00017 versus $0.00028 per case. Per-candidate Nouls worked; Choice ranking failed to retain multiple relevant items. Wider Jev pools could cost more, so cheaper unit inference did not guarantee cheaper workflows. Caveats: model judges, thresholds tuned on reported chat cases, one-day Jev timing, not deployed. [First-hand study](https://aerabrowser.com/news/agent-memory-doesnt-need-a-generator-typesafes-jev-vs-llm-on-400-real-tasks).

**3. Routing can be a bounded Choice, but compare identical units.** Taishi Morinaga's September 17 test called Jev directly for four difficulty tiers, ten repetitions each. Reported medians were 0.643–0.674 s at $0.000025–$0.000027 per call; all repeated samples matched the intended tier. Only four distinct straightforward inputs were tested. It was not integrated into NeMo Switchyard; prior LLM timing/cost came from a different setup and cost units were sessions versus calls. Adaptation: define operational tier criteria and test ambiguous boundaries; do not copy a claimed cost ratio across incompatible units. [First-hand test, Japanese](https://dev.classmethod.jp/articles/jev-for-llm-model-routing/).

**4. Make state meaningful; more structure is not automatically better.** AboveColin's Home Assistant integration was created September 17 (GitHub API date checked). It turns entity state into typed questions. Its small tests found that preprocessing numeric comparisons or explaining what readings meant helped; flat versus structured criteria tied at 12/15 intended answers in one caller-classification test. Adaptation: calculate exact facts in code, pass named semantic evidence, then ask the fuzzy judgment. Test structured rubrics against concise strings instead of treating JSON verbosity as a performance trick. [Author's code and measurements](https://github.com/AboveColin/HA-Jev).

**5. Context-sensitive secret triage is a testable Noul.** teyhouse published a September 17 test repo with 100 synthetic credential/non-credential snippets and category-level scoring, AUC and a review band. It deliberately isolates Jev from regex/provider verification. No new accuracy number is claimed here. Adaptation: judge whether a prefiltered item has credential semantics while retaining established scanning/verification controls. The experiment uses never-valid generated values; it is not justification to upload real secrets. [Author's repo](https://github.com/teyhouse/jev-secret-detection), [original post](https://www.reddit.com/r/LLMDevs/comments/1wiu1ej/typesafe_jev_secret_detection_test/).

**6. Independent idea dimensions can power instant interactive feedback.** A September 17 builder shared a demo evaluating an idea through roughly ten parallel criteria. The post claims a large speed advantage over a longer LLM evaluation, but does not provide a controlled quality/latency benchmark. Adaptation: ask distinct Scores for dimensions users can inspect, then weight them in code. A numeric composite is an opinionated rubric, not validation of a business. [Original author post](https://www.reddit.com/r/SideProject/comments/1wiw6tk/i_built_a_side_project_to_test_typesafes_jev/).

**7. Defining the rubric can change an answer more than switching the model.** A September 17 support-ticket comparison shows Boolean/Choice/Score through a gateway. Its urgency comparison gave Jev defined levels but the LLM an undefined enum. That makes the discrepancy evidence for rubric design, not proof that one model understood urgency better. Adaptation: give both models the same definitions; keep native Noul and gateway Boolean schemas distinct. [Author's gist](https://gist.github.com/yanisurbis/f15d4ef18e9a31de2fa10c0204bce298).

**8. Context management that respects the KV cache.** Nathan LeClaire of TypeSafe posted a September 17 thread of ideas for agents, with no code or measurements. The problem: coding agents depend on cached-prefix pricing, so switching models or idling a session busts the cache, and that makes routing and pruning expensive exactly when they would help. His proposal: let Jev judge what belongs in context in a cache-friendly way. The old prefix stays frozen; Jev evaluates only a backwards-looking tail for inclusion as it ages into the prefix; and any moment the cache is lost anyway (a model switch, returning after lunch) is a free chance to have Jev prune the whole context. He also suggests Jev-powered subagents that rip through logs, file trees or embedding hits and return only the relevant parts, so the main model's context is never polluted. Adaptation: per-item Nouls ("is this turn or tool result still needed for the current goal?") over the tail, with code owning the cache boundary and the rewrite trigger. Label: vendor-employee idea, unmeasured. [Thread](https://x.com/dotpem/status/2100609540500893882).

**9. Instructions and criteria can be JSON too.** In a September 17 reply, Nathan LeClaire of TypeSafe called structured instructions and criteria "very important for typesafe prompting optimization and unique to it". State, instructions and criteria can all be JSON, "but the former 2 are least obvious to be such": most people write `instructions: "classify this as a foo or bar"` with one-line criteria, when it is "potentially rich and powerful" to write `instructions: {"core": "...", "prev": [{}, {}, {}]}` and `criteria: {"foo": {"desc": "a foo", "examples": [...]}}`. The thread he replied to (@rasmus1610 and @kmad, September 16) suggested that DSPy optimizers such as GEPA should work on Jev questions unchanged and asked how sensitive the model is to description and schema changes; nobody in the thread reported a run. This is vendor advice consistent with the [structure docs](https://docs.typesafe.ai/primitives/advanced), and it sits alongside finding 4, where one small test saw flat and structured criteria tie. Adaptation: default to structure for ambiguous judgments, check it on labeled cases, and treat the wording and shape of instructions and criteria as the thing to optimize, by hand or with an optimizer, against a held-out set. [Post](https://x.com/dotpem/status/2100443292232307007).

### What transfers

The promising pattern is many narrow semantic judgments with shared evidence, followed by ordinary code. Use independent inclusion questions for multi-select; concrete levels for Scores; explicit alternatives for Choice; source IDs for extraction. The evidence supports trying more frequent feedback and larger candidate pools, while measuring the full system. It does not establish that Jev is always faster, always cheaper at a changed workload, or as accurate on every task.
